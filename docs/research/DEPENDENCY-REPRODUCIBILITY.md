# Dependency reproducibility

## Current state

The project declares `pnpm@10.0.0` in `package.json`, but a committed `pnpm-lock.yaml` is not present yet. The current CI therefore installs from semver ranges without a frozen dependency graph, and dependency caching is intentionally disabled.

Do not hand-author a pnpm lockfile. It must be generated by the declared pnpm version against the package manifest and registry metadata.

## Safe bootstrap

1. A maintainer runs the **Bootstrap pnpm lockfile** workflow from the GitHub Actions tab, selecting the `main` branch.
2. The workflow uses Node.js 22 and pnpm 10.0.0, resolves the dependency graph with lifecycle scripts disabled, and pushes the generated lockfile to a uniquely named automation branch.
3. It opens a pull request against `main`; review the resolved versions and merge only when acceptable.
4. After the lockfile is merged, update the main CI workflow to use `pnpm install --frozen-lockfile` and enable pnpm caching through `actions/setup-node`.

The workflow is manual-only, restricted to the `main` ref, and uses the repository-scoped ephemeral GitHub Actions token. It does not write the generated lockfile directly to `main`.

## Follow-up

- Keep `packageManager` pinned in `package.json`.
- Keep CI install frozen once the lockfile exists.
- Review dependency updates as explicit lockfile diffs.
- Do not run dependency lifecycle scripts as part of lockfile generation.
